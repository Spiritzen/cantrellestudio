/applications-metier-saas/

SECTION CIBLE UNIQUE :
MÉTHODE
Titre actuel :
« On ne commence pas par choisir une technologie. »

OBJECTIF
Refondre uniquement la section MÉTHODE pour la rendre :
- plus claire pour un visiteur non technique ;
- plus interactive ;
- plus premium ;
- mieux équilibrée visuellement ;
- cohérente avec la DA Cantrelle Studio.

Le problème actuel :
- `API / SERVICES` est orange par défaut sans raison compréhensible ;
- les autres étapes sont neutres ;
- il n’y a aucun hover utile ;
- le vocabulaire est trop technique ;
- la grande zone droite de la section est sous-exploitée ;
- l’ensemble ressemble davantage à un schéma technique qu’à une explication de méthode orientée client.

Nous voulons transformer cette section en PARCOURS INTERACTIF EN 6 ÉTAPES.

IMPORTANT :
ne pas toucher aux filaments, au background Ember, au Hero, à la carte PROJET ou aux autres sections.

==================================================
2. NOUVELLE INTENTION UX
==================================================

Desktop / pointeur précis :

À gauche :
6 étapes verticales, chacune sous forme de bloc / card compact.

À droite :
une zone explicative contextuelle.

Au repos :
- AUCUNE étape n’est orange par défaut ;
- toutes les étapes sont visuellement neutres ;
- la zone explicative droite peut afficher un message introductif simple, par exemple :
  « Survolez une étape pour comprendre comment le projet se construit. »
  ou formulation équivalente cohérente avec la DA.

Au hover / focus d’une étape :
- seule l’étape concernée passe en Ember ;
- léger lift / lumière / accent ;
- l’explication correspondante apparaît dans le panneau de droite ;
- les autres étapes restent neutres ;
- à la sortie de hover, l’étape revient à l’état neutre.

IMPORTANT :
pas d’état orange “bloqué” sans interaction.

==================================================
3. INTITULÉS À RENDRE COMPRÉHENSIBLES
==================================================

Remplacer les libellés techniques principaux par des formulations orientées client.

Utiliser cette direction :

1. VOTRE BESOIN
2. VOTRE FAÇON DE TRAVAILLER
3. LES INFORMATIONS UTILES
4. CONNEXIONS AVEC VOS OUTILS
5. L’INTERFACE
6. VÉRIFICATION & MISE EN LIGNE

IMPORTANT :
les termes techniques peuvent exister en second niveau si utiles,
mais jamais comme intitulé principal.

Exemples :
- « CRM »
- « API »
- « back-office »
- « SaaS »

peuvent être mentionnés dans une explication secondaire,
mais seulement si immédiatement compréhensibles dans le contexte.

==================================================
4. CONTENU EXPLICATIF AU HOVER
==================================================

Créer une explication claire pour chaque étape.

Base éditoriale recommandée :

ÉTAPE 01 — VOTRE BESOIN
Titre panneau :
« Comprendre ce qui doit vraiment être amélioré »

Texte :
« On commence par identifier ce qui vous fait perdre du temps, ce qui crée des erreurs ou ce qui complique votre organisation : suivi clients, doubles saisies, planning, facturation ou circulation de l’information. »

ÉTAPE 02 — VOTRE FAÇON DE TRAVAILLER
Titre panneau :
« Respecter votre fonctionnement métier »

Texte :
« On observe comment votre activité fonctionne réellement : qui fait quoi, dans quel ordre, avec quelles règles et quelles contraintes. L’outil doit s’adapter à votre métier, pas l’inverse. »

ÉTAPE 03 — LES INFORMATIONS UTILES
Titre panneau :
« Structurer les bonnes données »

Texte :
« Clients, produits, rendez-vous, documents ou historiques : on détermine quelles informations sont réellement utiles et comment elles doivent être organisées. »

ÉTAPE 04 — CONNEXIONS AVEC VOS OUTILS
Titre panneau :
« Faire communiquer ce qui doit l’être »

Texte :
« Si nécessaire, votre application peut échanger avec votre site, votre comptabilité, un système de paiement ou d’autres services déjà utilisés. »

ÉTAPE 05 — L’INTERFACE
Titre panneau :
« Concevoir des écrans simples à utiliser »

Texte :
« On construit les écrans autour des usages quotidiens : retrouver une information, créer un document, suivre une activité ou réaliser une action sans complexité inutile. »

ÉTAPE 06 — VÉRIFICATION & MISE EN LIGNE
Titre panneau :
« Tester avant de livrer »

Texte :
« Les parcours importants, les droits d’accès et le bon fonctionnement sont vérifiés avant la mise en ligne, puis ajustés si nécessaire. »

Tu peux ajuster légèrement les formulations si cela améliore la fluidité,
mais le sens doit rester exactement celui-ci :
langage client, pas jargon développeur.

==================================================
5. COMPOSITION DESKTOP
==================================================

Sur desktop >= 900px :

- section en 2 colonnes équilibrées ;
- colonne gauche : parcours vertical en 6 étapes ;
- colonne droite : panneau explicatif ;
- utiliser l’espace aujourd’hui vide à droite ;
- panneau droit aligné visuellement avec la liste ;
- éviter une card géante vide.

Composition recommandée :
- gauche ~45%
- droite ~55%
ou proportions proches selon le layout réel.

Le panneau explicatif doit être suffisamment présent,
mais rester secondaire par rapport au grand titre de section.

==================================================
6. DESIGN DES ÉTAPES
==================================================

Au repos :
- surface sombre cohérente avec Cantrelle Studio ;
- bordure fine ;
- texte ivoire ;
- numéro discret ;
- aucun orange actif par défaut.

Au hover / focus :
- bordure Ember ;
- numéro Ember ;
- texte principal peut devenir légèrement plus lumineux ;
- lift léger : environ -3px à -5px ;
- glow très discret ;
- transition 220–300ms environ.

NE PAS :
- faire tourner les cards ;
- utiliser un scale fort ;
- faire clignoter ;
- ajouter une animation permanente ;
- transformer cela en menu flashy.

==================================================
7. PANNEAU EXPLICATIF DROIT
==================================================

Le panneau droit doit s’intégrer à la DA.

Direction recommandée :
- surface sombre légèrement translucide ;
- border fine ;
- radius cohérent avec les tokens du site ;
- petit label de type « ÉTAPE 01 » en Ember ;
- titre explicatif ivoire ;
- texte secondaire gris clair ;
- éventuellement une fine ligne Ember ou un micro-accent.

Transition entre deux explications :
- opacity 0 → 1
- légère translation Y ou X de 6–10px maximum
- pas de gros mouvement

Pas de carrousel.
Pas de modal.
Pas de tooltip flottante.

==================================================
8. ÉTAT INITIAL DU PANNEAU
==================================================

Au chargement :
AUCUNE étape active.

Le panneau peut afficher un état introductif :

Label :
« NOTRE MÉTHODE »

Titre :
« Chaque choix technique part d’un besoin concret. »

Texte :
« Survolez une étape pour voir comment le projet se construit, du besoin initial jusqu’à la mise en ligne. »

Cette formulation peut être adaptée légèrement,
mais doit rester simple et orientée client.

==================================================
9. MOBILE / TABLETTE — PAS DE HOVER
==================================================

Sous tablette / mobile :

Ne pas dépendre du hover.

Comportement attendu :
- liste verticale ;
- chaque étape est cliquable/tappable ;
- l’explication de l’étape s’ouvre juste dessous sous forme d’accordéon ;
- une seule étape ouverte à la fois ;
- au premier chargement : toutes fermées.

IMPORTANT :
- accessible au clavier ;
- pas de hover-only ;
- aucune information essentielle inaccessible au tactile.

==================================================
10. ACCESSIBILITÉ
==================================================

Utiliser une structure accessible.

Si boutons :
- vrais `<button>`
- aria-expanded sur mobile si accordéon
- aria-controls si pertinent
- focus visible

Au clavier desktop :
- Tab permet de parcourir les 6 étapes ;
- focus déclenche la même explication que hover ;
- blur revient à l’état neutre si aucune autre étape n’est active.

Ne jamais dépendre uniquement de la couleur pour indiquer l’état actif :
ajouter aussi un changement de bordure / position / accent.

==================================================
11. LOGIQUE D’ÉTAT
==================================================

Choisir l’implémentation la plus simple et robuste.

Possible :
- JS vanilla dans Astro
- ou petit composant React si déjà cohérent avec l’architecture

Préférence :
éviter de créer une nouvelle dépendance.

État attendu :
- `activeStep = null` au repos
- hover/focus/tap => activeStep = étape
- mouseleave/blur desktop => retour null
- mobile tap => toggle ou remplacement de l’étape ouverte

Ne pas créer une logique complexe inutile.
